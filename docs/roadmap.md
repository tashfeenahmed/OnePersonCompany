# Roadmap — capability gaps

One Person Company grew out of WorkDash, a single-owner operations system the
same author ran before it, and `server/src/integrations/migrate/` is a working
importer for a WorkDash installation. This document is the gap list from
comparing the two source trees on 6 September 2026: what WorkDash could do that
this cannot yet, in priority order. Links marked `workdash:` point into that
other tree and will not resolve here; they are kept because they say where the
comparison was made.

It is a source comparison, not a live-service acceptance test. Provider
credentials, production machines, publishing permissions and live financial data
were not exercised. "Workdash has" means an implementation exists in that
repository; it does not mean the feature was configured or working. Where this
document and the current code disagree, the code wins.

**Main finding:** One Person Company already covers much of WorkDash's breadth.
The larger gaps are complete workflows, deeper measurements and unattended
operation — not missing sidebar pages.

**Status:** Missing = no equivalent application implementation found; Partial = a related implementation exists but lacks the stated capability; Migration = work needed to replace the existing installation. These are capability gaps, not 45 confirmed bugs. Some are deliberate simplifications worth keeping.

**Priority:** P1 = address first for a dependable replacement; P2 = valuable next; P3 = optional or dependent on how you operate. Priorities are my assessment, not an existing project commitment.

## Agent and recurring work

| # | Missing piece | OPC status | Workdash comparison and practical impact | What to add | Priority |
|---|---|---|---|---|---|
| 1 | OS isolation for agents | Missing | Workdash provides a separate Hermes container, restricted network, and scoped dashboard access. OPC explicitly documents that an unrestricted agent under the same OS account can read credential files or change the database, bypassing API owner controls. [Workdash](workdash:deploy/systemd-units.txt:813) · [OPC](./README.md:67) | A container or separate OS identity with limited mounts and scoped tool access. Keep owner permissions enforced outside the agent's filesystem reach. | P1 |
| 2 | Tool use without a separate agent runtime | Missing | Workdash has its own model/tool execution loop. OPC's direct model-provider fallback is explicitly text-only; business tools require a connected agent such as Hermes or OpenClaw. Connecting a model key alone therefore does not make chat capable of checking live business data. [Workdash](workdash:agent/agent.js:610) · [OPC](./server/src/routes/chat.ts:185) | Either implement a bounded tool loop for direct providers or make the runtime requirement unmistakable during setup. This is conditional on wanting model-only installations. | P2 |
| 3 | Chat continuation after reload or disconnect | Partial | Workdash separates the agent run from its browser subscription and buffers events for reattachment. OPC supports concurrent chats and saved partial answers, but its client explicitly says a reload cannot reattach to an active turn. A long investigation can be cut short by closing or reloading the tab. [Workdash](workdash:agent/runs.js:1) · [OPC](./client/src/pages/Chat.tsx:170) | Server-owned chat jobs, run IDs, reconnectable event streams, and explicit cancellation. Preserve the existing separate background sub-agent run queue. | P1 |
| 4 | Consistent size limits on agent tool responses | Partial | Workdash's MCP layer exposes curated summaries/details and a response ceiling. OPC forwards the tool response body whole, including complete board responses. Individual endpoints may limit rows, but there is no comparable common response budget. Large datasets can consume excessive context or obscure the answer. [Workdash](workdash:agent/hermesmcp.js:1) · [OPC](./server/src/skills/mcp.ts:314) | Summary-first views, pagination, selected fields, and a common size budget with explicit continuation. Avoid cutting JSON in the middle. | P1 |
| 5 | Coordinated nightly pipeline and schedule controls | Partial | Workdash coordinates many stages, tracks stage outcomes, controls models and limits, and supports blackout windows. OPC has scheduled rounds and separate feature timers, but rounds chiefly dispatch selected roles across ventures. It lacks an equivalent combined stage plan and overnight result. [Workdash stages](workdash:agent/schedule.js:71) · [Workdash execution](workdash:agent/nightly.js:1507) · [OPC](./server/src/integrations/chief/rounds.ts:65) | One visible schedule with dependencies, per-stage enablement/budgets, blackout periods, due dates, and a record of completed, skipped, and failed stages. Reuse existing executors. | P1 |
| 6 | Portfolio-wide and project-wide action synthesis | Partial | Workdash's gardening and project-gardening passes compare multiple sources, rotate coverage, and gate proposed tasks. OPC rounds rotate specialist jobs; goals, memory, and briefings exist, but that is not an equivalent cross-source pass deciding the best next action for each venture. [Workdash](workdash:agent/projectgarden.js:823) · [Task gate](workdash:agent/gardening.js:636) · [OPC](./server/src/integrations/chief/rounds.ts:331) | A synthesis pass that reads current evidence and existing tasks, ranks opportunities, and files a small number of concrete, deduplicated actions. | P1 |
| 7 | Evidence-backed product knowledge | Missing | Workdash's “soul” records distinguish repository facts, measured evidence, owner statements, and proposed facts. OPC has venture descriptions, brand extraction, standing instructions, and dated memory, but no equivalent evidence-tiered product knowledge store. Agents can miss product capabilities that are visible in the code. [Workdash](workdash:agent/soul.js:783) · [Repository extraction](workdash:agent/soul.js:1231) · [OPC memory](./server/src/integrations/chief/memory.ts:1) | Map ventures to repositories; store facts with source references, observation dates, confidence, owner corrections, and refresh rules. Supply these facts to research, Studio, and planning. | P1 |
| 8 | Application-level delivery of agent cron results | Partial | Workdash explicitly ticks native Hermes jobs and relays their results to Telegram with persistent delivery state. OPC starts a managed gateway and has its own timers, but no equivalent OPC adapter was found for reading arbitrary native cron results and relaying them. This does **not** prove native Hermes scheduling fails. [Workdash](workdash:agent/hermescron.js:1) · [OPC runtime](./server/src/agents/instance.ts:1) | Expose native scheduled-job status and results, verify delivery through the selected runtime, and bridge results where needed. Preserve successful native behavior rather than adding a second scheduler blindly. | P2 |

| Media and operations | Image Studio, faceless/shorts video, Autopilot generation, capture/QA heuristics, uptime, backups, snapshots, and workstation controls. | Publishing, additional formats, deeper QA, and shared power management remain incomplete. |
| Current navigation work | Sidebar sections, common pinned pages/sessions, reorder support, and custom module icons are already in the current working tree. | These are intentional OPC UX choices, not Workdash parity gaps. |

## Suggested implementation order

1. **Make the foundation dependable:** agent isolation, reconnectable chat, bounded tool responses, product adapters, and unattended service setup. Design migration before accumulating parallel histories.
2. **Make revenue actionable:** operating costs, mobile health/reviews, customer recovery and dispute cases, plus reliable event notifications.
3. **Finish delivery workflows:** product-domain mail, factual nurture drafts, social publishing, and scheduled publication. Connect outputs to real destinations and recorded results.
4. **Make the agent proactive:** evidence-backed product knowledge, coordinated nightly stages, and portfolio/project action synthesis using the existing specialist tools.
5. **Add depth and optional formats:** richer analytics and ad creatives, SEO follow-up, campaign production, enhanced video, visual QA, and then cosmetic customization.

Workdash should be treated as a reference, not copied wholesale. Preserve OPC's explicit handling of missing data, currency separation, owner controls, and generic integration architecture. Avoid carrying over historical shortcuts such as mixing MRR with store payout months, treating project-wide revenue as attributed ROAS, or using unreliable search hits as proof of a directory listing.
